Void tracking — including flag-sync false voids

Payment window & void — 90 days known + 45 days grace See logic ▸

Customer agrees a final payment date = approval + 90 days (the only deadline the customer knows). An extra 45-day grace follows (customer is NOT told). If the full amount isn't paid by Day 135, the case voids.

Payment & void — reconciled against approved cases (Aug 2026)

Every approved case must land in exactly one bucket below — the buckets add back to the approved total.

Why it matters: Starting from the approved cases, each one is either paid-and-settled, still inside its payment window, in the hidden 45-day grace, or voided. Because the buckets sum back to approved, nothing is lost. The 45-day grace is the recovery window the customer doesn’t know about — a proactive call there can save a case. Genuine voids are expected; false voids (full amount received but flag not synced) must be zero.

Logic & calculation reference

Monthly cohort waterfall & outcome reconciliation ▸ You are viewing this ◂ Back

  • Cohort = all cases where settlement_initiated_date falls in the selected month.
  • Each stage counts that same cohort as it reaches the stage (a subset — the funnel narrows).
  • Consent initiated = consent raised, digital or manual. Consent gap = Initiated − Consent initiated.
  • Withdrawal can happen at several points — after initiation, after consent, or after recommendation (any time before approval).
  • Outcome reconciliation: Withdrawn(after init) + Withdrawn(after consent) + Withdrawn(after reco) + In progress + Approved = Initiated. Every case lands in exactly one terminal bucket, so the total ties back to the top funnel.
  • Counts are at case level (one row = one unique settlement case).

Who was sent the SMS — party waterfall ▸ You are viewing this ◂ Back

  • Applies to informational SMS (initiated / approved / closed / void) — sent to both parties.
  • Consent SMS is excluded here — it goes to the primary applicant only (see Consent logic).
  • Applicant: Sent = Top − (number missing) − (not sent)
  • Co-applicant: Present = Top − (no co-applicant)
  • Co-applicant: Unique-to-SMS = Present − (number SAME as applicant) − (number missing)
  • Co-applicant: Sent = Unique-to-SMS − (not sent)
  • Rule: only unique numbers are messaged — a co-applicant whose number equals the applicant’s is correctly not sent a duplicate.

Consent completeness & consent SMS ▸ You are viewing this ◂ Back

  • Consent is taken from the primary applicant only. A consent-request SMS is never sent to the co-applicant.
  • Co-applicant receives informational SMS only on: initiated, cancelled (withdrawn), closed, void.
  • Consent SMS gap = Initiated applicants − Consent SMS sent → applicants initiated but with no consent SMS (investigate).
  • Consent completeness: Digital + Manual + No-consent = Initiated (must balance).
  • “No consent on record” = initiated cases with neither a digital nor a manual consent.

Stage communication side-by-side ▸ You are viewing this ◂ Back

  • Same SMS breakup as the click-drawer, laid out with one column per stage and parameters as rows.
  • Follows the Stage Flow Month/Day toggle: in day-wise mode every number is scaled to the selected day.
  • Not sent = number missing/NULL + present-but-not-sent, per stage.
  • Consent is applicant only → its co-applicant cell shows N/A.

Consent parameters breakup ▸ You are viewing this ◂ Back

  • Consent sent = Digitally initiated + Manually initiated (includes the “both” cases once).
  • Sub-states track where consent stalls: awaited (MTD), acknowledged, rejected (by customer / by QC), not received, pending >24h / >48h.
  • Not moved to DMS = consent captured but the signed document isn’t filed in the document store (audit gap).

Day-on-day cumulative ▸ You are viewing this ◂ Back

  • Running total of “SMS not sent” added each day, within the selected month.
  • Cumulative(day) = Cumulative(day−1) + new not-sent on that day.
  • A steepening curve = the backlog is accelerating; a flattening curve = under control.

Payment window & void logic ▸ You are viewing this ◂ Back

  • Final payment date (known to customer) = Approval date + 90 days. Customer may pay the full agreed amount any time within these 90 days.
  • Grace end = Approval date + 90 + 45 = +135 days. Customer can still pay in the 45-day grace, but is not told it exists.
  • Void condition: full agreed amount not received by Day 135 → case voids.
  • Genuine void = no payment, or partial only, by Day 135.
  • False void = full amount actually received in Indus, but the match flag did not sync to LMS in time, so the case wrongly voided at Day 135. Target = 0 — reverse and re-settle.
  • Ageing buckets: within 90d · approaching Day 90 · in grace (90–135) · voided at 135.
  • Void rate = Voided cases ÷ Approved cases (per month).

Flag-sync SLA (Indus → LMS) ▸ You are viewing this ◂ Back

  • Sync time = LMS flag-received timestamp − Indus approval timestamp
  • Target ≤ 5 min; amber 5–7 min; breach > 7 min.
  • Breaches are the leading cause of false voids — a slow flag means the settlement flag is not raised on time.

Operational control tripwires ▸ You are viewing this ◂ Back

  • Each control’s healthy value is 0 (or “monitor/reduce” for the consent-outcome rows).
  • Pending ageing: time now − stage entry time exceeding the SLA (consent >24h / >48h, recommendation >6d, approval >4d).
  • DMS: consent / approval letter captured but not moved to DMS → document not filed for audit.
  • Trend compares this period vs last: ▲ rising (worse), ▼ falling (better), ▬ flat.
  • Slicers (Month / Vertical / P-C Flag) scope every control.

Pre-payment reminder (proposed) ▸ You are viewing this ◂ Back

  • Status: proposed — not yet in the live workflow.
  • T-1 reminder date = Payment date − 1 day (day-before nudge).
  • T-0 reminder date = Payment date (same-day nudge).
  • Reminder goes to the primary applicant (payment is the applicant’s responsibility).
  • Works for a single final payment or multiple tranche dates — one T-1/T-0 pair per payment date.
  • Goal: reduce avoidable voids caused by the customer simply forgetting the date.

Closure tolerance (collected vs agreed) ▸ You are viewing this ◂ Back

  • Shortfall = Agreed amount − Collected amount
  • If Shortfall ≤ ₹300 → the case is allowed to close (must not void over a small shortfall). Max tolerance = ₹300.
  • Control failure = a case that voided even though Shortfall ≤ ₹300 → should have auto-closed.
  • If Shortfall > ₹300 → not auto-closed; routed for manual review.
